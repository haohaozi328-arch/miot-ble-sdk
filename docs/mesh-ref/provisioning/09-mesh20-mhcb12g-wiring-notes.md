# 09 Mesh 2.0 模组（MHCB12G）接线与观测实测

> 2026-11-27。对象：86 开关板上的 **MHCB12G**（米家 Mesh 2.0 模组），
> MAC `14:D8:81:E6:95:3C`，PID `0x6ABC`（27324）。已经米家正常配网，
> 小爱音箱语音开关正常。本文记录**接线脚位**、**串口/广播两路观测结果**，
> 以及由此得到的「Mesh 2.0 控制链路本地不可观测」结论。

## 1. 接线脚位（从规格书原理图逐脚核对）

来源：模组规格书 `img_07`（应用电路）、`img_32`（设计注意），见工作区 `pdfimgs/`。

| 功能 | IO / 脚号 | 板上测试点 |
|---|---|---|
| LOG（日志） | **P0_3 / 脚23** | J5 |
| UART TXD | **P3_0 / 脚12** | J4 |
| UART RXD | **P3_1 / 脚13** | J3（此前文档写 P1_3，已订正） |
| RESET | 脚34（无测试点，需直接从模组焊盘引） | — |
| 3V3 | VDDIO 脚25 / VDD-BAT 脚14 | J2 |
| GND | 脚1/9/24/26/35 | J1 |

要点：

- **LOG（P0_3）和 TXD（P3_0）都是模组往外发的信号，不能短接**，一个 TTL 只能二选一。
- **不要用 TTL 的 3V3 给模组供电**：USB-TTL 的板上 LDO 一般只有 50–100mA，
  Mesh 模组射频发射瞬时电流会把它拉到欠压，表现为 1 秒一次的 `Reset by Power`
  复位循环（在 Mesh 1.0 灯泡上实测过）。规格书要求供电能力 ≥500mA、纹波 <100mV。
- 本板是 86 开关，AC 市电侧与低压侧分离；第一阶段只动低压侧。
- SIO/UART 线建议串 200Ω，天线周围 15mm 净空。

### 本次实际接法

单个 USB-TTL，接 UART 双向口（不接 LOG）：

```
TTL RX  ←  P3_0 (TXD / 脚12 / J4)
TTL TX  →  P3_1 (RXD / 脚13 / J3)
TTL GND ↔  GND
TTL 3V3 →  不接（板子自供电）
```

## 2. 两路观测结果（配网 + 小爱语音控制期间）

抓取窗口 150s（广播）/ 200s（UART），覆盖米家识别配网、小爱语音开关灯 1 次。

### UART（P3_0 / P3_1）：全程 0 字节

```
_mhcb_prov_uart.log: 0 bytes
```

试过 115200 / 9600 / 921600 / 57600 四个波特率，发 `AT`、`get_down` 等探测命令，
全部零回音。结合 Mesh 1.0 灯泡的结论（应用固件 UART 只做日志口、启动窗口后 `close uart`），
**P3_0/P3_1 这条口在正常配网和控制流程中不吐任何协议内容**——
它不是「假 MCU」那条 `model`/`get_down` 控制协议口。想看设备内部在想什么，只能靠 LOG(P0_3) 口。

### BLE 广播（0xFE95）：36 帧，形态恒定

全程只收到一种帧：

```
14:D8:81:E6:95:3C  FE95  90 54 bc 6a 00 3c 95 e6 81 d8 14 0e 00
```

解码：

| 字段 | 值 | 说明 |
|---|---|---|
| fc | `0x5490` | ver=5, auth=1, **registered=0**, **mesh=1**, solicited=0 |
| pid | `0x6ABC` | 27324 |
| mac | `14:D8:81:E6:95:3C` | 与设备地址一致 |
| 尾部 | `0e 00` | 状态/事件字节 |

三个观察：

1. **registered 位恒为 0**：设备已经配网成功、正常受控，但广播里的 registered 仍是 0。
   与 Mesh 1.0 灯泡一致——**registered 位不能用来判断 mesh 设备是否已配网**。
2. **控制前后广播帧字节完全相同**：小爱语音开关灯 1 次，36 帧从头到尾都是
   `...14 0e 00`，没有任何 `fc` 变化或新增形态。**Mesh 2.0 的控制链路在本地广播侧不可观测**。
3. **未出现 0x1827/0x1828 未配网 beacon**：设备已配网，这不意外。

### 2.1 重新配网：未配网 → 已配网的广播帧切换（2026-11-27 补测）

恢复出厂后重新走米家配网，抓到完整切换（`_mhcb_rebind2_adv.log`）：

```
t= 0.17~26.17s  未配网(solicited)  d0 5c bc 6a 00 3c 95 e6 81 d8 14 00 80 08 b2 72 d3 79 00 00 00 00 02 00  (24B)
   [27~36s 广播空窗 ≈11s：App 配网握手中，设备停发 MiBeacon]
t=37.15~51.91s  已配网            90 54 bc 6a 00 3c 95 e6 81 d8 14 0e 00                            (13B)
```

| 字段 | 未配网 | 已配网 |
|---|---|---|
| fc | `0x5CD0`：ver=5, auth=1, reg=0, **solicited=1**, mesh=1 | `0x5490`：solicited=0 |
| 帧长 | 24B（多 11B） | 13B |
| 尾部 | `00 80 08 b2 72 d3 79 00 00 00 00 02 00` | `0e 00` |

三个结论：

1. **Mesh 2.0 的配网窗口信号 = `solicited` 位 1→0 + 帧由 24B 缩到 13B**，
   与 Mesh 1.0 灯泡的 payload `08 02 00 → 08 0E 00` 是同类现象但编码不同。
   这是判断 Mesh 2.0 设备是否处于待配网态的可靠广播侧判据。
2. **配网握手期间有约 11 秒广播空窗**——设备停止 MiBeacon，可直接读出来。
3. 尾部多出的 11B（`00 80 08 b2 72 d3 79 00 00 00 00 02 00`）只在未配网态出现，
   其中 `b2 72 d3 79` 疑似随机挑战/配网会话标识，每次恢复出厂可能不同，未深挖。

UART 在配网期间仍为 0 字节；此前抓到的 `Firmware for APP / RESET Reason: HW` 是**硬件复位**时的引导打印（重复 4 次 = 复位 4 次），不是配网事件。

## 3. 结论与定位

- **接线研究这一步的信息增益已兑现**：脚位映射确认、UART 口性质确认（非 MCU 协议口）、
  广播恒定形态确认。剩下的深挖点只剩 LOG(P0_3) 口——需要再接一个 TTL 单独抓，
  本次单 TTL 接在 P3_0/P3_1 上，看不到启动日志。
- **Mesh 2.0 配网走 BLE 扩展广播 + 三元组双向认证**（见 `official-findings.md`），
  配网握手的设备侧过程不走 UART；但**配网状态切换在明文 MiBeacon 广播里可见**
  （solicited 位 + 帧长变化，见 §2.1）。要抓握手报文细节，只能抓 LOG 口或做手机 HCI snoop。
- **不改结论**：伪装 Mesh 设备的三堵墙（私有配网、证书链、物理私钥）依然成立；
  这颗模组本身是合法身份，已配网可用，走「借壳/官方模组」是正路。

## 4. 复现步骤

1. 单 TTL 接 P3_0(TX)/P3_1(RX)/GND，不接 3V3；板子低压侧自供电。
2. 挂抓：`python -c '...serial.COM5...'` 或 `tools/serial_tap.py COM5` 抓 UART。
3. 另开一路：`python tools/mesh/watch_mhcb_adv.py 150 _mhcb_adv.log` 抓全量广播。
4. 米家配网 / 小爱语音控制，事后对比广播帧种类（`sort | uniq -c`）与 UART 字节数。
