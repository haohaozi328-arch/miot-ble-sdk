# 纯净 App 兼容矩阵 —— 官方原版米家 App，不装任何模块

> 目的：回答一个问题——**别人拿到这台设备，用官方原版 App 能不能添加成功？**
> 结论只取决于设备档案走哪条认证路径，与固件是谁编译的无关。

## 认证路径只有三种

| 路径 | 触发依据 | 谁校验 | 本 SDK 已实现 |
|---|---|---|---|
| **标准认证**（ECDH P-256 REGISTER + HKDF LOGIN） | 广播 FC 的 authMode = 2 | 设备端本地完成，云端只按 PID 建档 | ✅ 完整 |
| **legacy PSK**（ECDH + `smartcfg-*` 标签的 HKDF，**非**对称挑战应答） | App 按型号判定走 PSK 连接器 | 设备端需实现 PSK 握手 | ⚠️ **已实现，未实测**（[帧格式与开关](psk-auth.md)） |
| **广播型**（MiBeacon，不建连接） | 无 GATT 会话 | 网关收广播即可 | ✅ 完整 |

关键事实：**走哪条路径由 App 按型号决定，不由设备挑选。**
所以「某型号在纯净 App 下能不能绑」，答案是固定的——与有没有调试模块无关。

## 本表的口径说明（重要）

- 矩阵按**认证路径**静态判定：标准认证由设备端本地完成，App 原版即可；
  PSK 路径的握手代码已实现（`MIOT_AUTH_MODE_PSK`），但**还缺一次真机实测**，
  所以第 4、5 项只能标「待实测」而不是「能」。实测开关见 [psk-auth.md](psk-auth.md) §6。
- 历史实机记录（`docs/testing.md`）的测试环境曾带有调试辅助模块，
  **不能直接作为"纯净 App 可绑定"的证据**。因此第 7 项标「待复核」。
- 上表第 1~3、6 项之所以标"能"，是因为它们的绑定完成标志
  （`REGISTER COMPLETE` / `BOND confirmed`）出现在**设备端**串口，
  且认证流程不含 PSK 步骤。

## 怎么自己复核一遍（20 分钟）

不安装任何模块，用官方原版 App：

```bash
# 1. 删除设备（我的 → 设备管理 → 删除）
# 2. 重启 App，确保没有残留连接
adb shell am force-stop com.xiaomi.smarthome
# 3. 重新扫描添加，观察串口
idf.py -p <PORT> monitor
```

判据：

| 串口 | 含义 |
|---|---|
| `REGISTER COMPLETE (result 0x11)` + `REGISTER: did stored` | 标准认证，纯净 App 通过 |
| 只出现 `CMD_REGISTER(0xA2)` 后无后续 | 可能被要求走 PSK，或 92B 帧解析差异 |
| `PSK: start frame … captured` | 判定为 PSK 设备，握手已开始（看后续 `PSK:` 行） |
| `PSK: unhandled <n>B (psk_state=…)` | PSK 分支收到未识别帧，开 `psk_trace` 抓原始 hex |
| `dispatch: no consumer (pkg=...)` | 两种链都不认的包，通常是对应档案选错了 |
| 完全无认证日志 | App 没连上，先查广播与 GATT |

把结果回填本表并注明 App 版本与账号区域，是对后来者最有用的一条信息。

## 给使用者的实话

如果你要的是「买个板子刷完就能加进米家」，**选第 2 或第 12 项**——
它们的认证路径完全在设备端，不依赖任何未验证环节。
驱蚊器 / 夜灯重绑走 PSK：代码已经实现（与标准认证共用同一套 ECDH，
只换 HKDF 标签，多一帧 `0x04` 签名），但**还没有人跑通过一次真机实测**，
所以现在不能承诺"能加"。愿意当第一个验证者的话，按 [psk-auth.md](psk-auth.md) §6 开
`psk_trace` 走一遍，把串口日志提 issue 即可。
